# معماری «زمین چمن ایرانیان»

## لایه‌ها
- **UI (`ui/`, `feature/`)**: Jetpack Compose + Material 3، کاملاً RTL. هر صفحه یک ViewModel دارد (MVVM).
- **Domain (`domain/`)**: قواعد خالص بدون Android: الگوی تکرار قرارداد (`Contract.matches`)، بازه‌های زمانی (`Period`).
- **Data (`data/`)**: Room (`db/`)، Repositoryها، ذخیره‌ی فایل فاکتور، Backup/Restore، خروجی PDF/Excel.
- **Core (`core/`)**: خطاها با پیام فارسی، تقویم شمسی، قالب‌بندی پول و ارقام، هش رمز.
- **DI**: `AppContainer` دستی (بدون Hilt) تا وابستگی و پیچیدگی Build کمتر باشد.

## جدول‌ها
| جدول | توضیح |
|---|---|
| customers | مشتری (حذف نرم با `deletedAt`) |
| contracts | قرارداد دوره‌ای = فقط «الگو» (زوج/فرد/روزهای هفته + ساعت + بازه‌ی تاریخ + مبلغ) |
| bookings | هر رزرو یا هر جلسه؛ `contractId` برای جلسه‌ی قرارداد؛ زمان‌ها epoch میلی‌ثانیه |
| payments | پرداخت‌ها، **تنها منبع درآمد** |
| expenses / attachments | هزینه و فاکتورهای پیوست (فایل در `filesDir/attachments`) |
| activity_log | آخرین فعالیت‌ها برای داشبورد |
| app_settings | نام کاربری، هش رمز، زمان قفل خودکار (داخل DB تا Backup آن‌ها را هم ببرد) |

قواعد مهم:
- **بدهی ذخیره نمی‌شود**؛ همیشه `totalAmount − مجموع پرداخت‌ها` محاسبه می‌شود (رزروهای لغوشده حساب نمی‌شوند).
- **درآمد دوبار شمرده نمی‌شود**: لیست تراکنش مالی یک `UNION ALL` از payments و expenses است، نه جدول جدا.
- **قرارداد جلسه نمی‌سازد.** جلسه فقط وقتی ثبت می‌شود که اپراتور «ثبت جلسه» را بزند؛ آمار هر قرارداد از همین جلسه‌ها محاسبه می‌شود.
- **تداخل زمانی**: رزروی که بازه‌اش با رزرو فعال دیگری اشتراک داشته باشد رد می‌شود (پشت‌سرهم بودن مجاز است). هنگام بازگردانی از سطل بازیافت هم دوباره چک می‌شود.
- زوج/فرد بر اساس **روز ماه شمسی** است. روزهای هفته: ۰ = شنبه … ۶ = جمعه.
- حذف مشتری وقتی رزرو یا قرارداد فعال دارد ممنوع است. همه‌ی حذف‌ها اول به سطل بازیافت می‌روند و تأیید می‌خواهند.

## قفل و ورود
رمز با PBKDF2-HMAC-SHA256 (۱۲۰٬۰۰۰ دور، salt تصادفی) هش می‌شود. بعد از ۵ تلاش ناموفق ۳۰ ثانیه ورود مسدود می‌شود.
قفل خودکار هم با عدم تعامل و هم با رفتن اپ به پس‌زمینه کار می‌کند.

## فرمت Backup
فایل ZIP:
```
manifest.json   {format, dbVersion, createdAt, dbSha256, attachments:[{name,sha256}]}
db/zamin_chaman.db
attachments/<uuid>.<ext>
```
بازیابی: فایل در پوشه‌ی موقت باز می‌شود (نام ورودی‌ها اعتبارسنجی می‌شود) ← manifest، SHA-256، نسخه و `PRAGMA integrity_check`
بررسی می‌شود ← از اطلاعات فعلی یک Backup امن در `filesDir/internal_backups` ساخته می‌شود ← جایگزینی با امکان rollback ← راه‌اندازی مجدد اپ.
Backupِ نسخه‌ی قدیمی‌تر بعد از بازیابی با Migrationها به‌روز می‌شود. Backupِ نسخه‌ی جدیدتر رد می‌شود.

## Migration (چطور ساختار را عوض کنیم)
1. Entityها را تغییر دهید و `DB_VERSION` را زیاد کنید.
2. در `Migrations.kt` (`AppDatabase.kt`) یک `Migration(1, 2)` با SQL ساده (ALTER/CREATE) بنویسید و در `ALL` بگذارید.
3. یک بار Build کنید تا `app/schemas/2.json` ساخته شود؛ هر دو فایل schema را commit کنید.
4. `MigrationTest` را برای ۱→۲ کامل کنید.
قبل از اجرای Migration، یک کپی از دیتابیس قدیمی در `filesDir/internal_backups` نگه داشته می‌شود (۳ نسخه‌ی آخر).

## گزارش‌گیری
فیلترها ترکیب‌پذیرند: بازه‌ی تاریخ ∧ زوج/فرد ∧ روزهای هفته. بخش‌ها: درآمد، هزینه، اجاره تایم، بدهی‌ها، تسویه‌شده‌ها، جلسات انجام‌شده.
خروجی PDF با `PdfDocument` اندروید و خروجی Excel با یک نویسنده‌ی `.xlsx` ساده (بدون کتابخانه‌ی خارجی) ساخته می‌شود.

## محدودیت‌های شناخته‌شده
- ساعت پایان باید در همان روزِ شروع باشد (رزرو عبورکننده از نیمه‌شب پشتیبانی نمی‌شود).
- قراردادها با هم تداخل‌یابی نمی‌شوند؛ تداخل هنگام ثبت هر جلسه چک می‌شود.
- در PDF از فونت سیستم استفاده می‌شود؛ اگر چیدمان حروف در گوشی خاصی ایراد داشت، فونت وزیرمتن را در `PdfExporter` اضافه کنید.
- عکس فاکتور بدون فشرده‌سازی ذخیره می‌شود.
